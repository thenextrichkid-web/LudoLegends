6. Can a new user register successfully?
   ANSWER: PARTIALLY. New users are auto-created when OTP is requested, but the
   OTP verify flow has a CRITICAL BUG: the verify endpoint does NOT validate the

7. Can users log in successfully?
   ANSWER: YES — in the sense that calling verify_otp with any 6-digit code

8. Can users log out?
   ANSWER: YES — Flutter secure storage tokens are deleted on logout. Profile

9. Is the session maintained after reopening the app?
   ANSWER: YES — JWT tokens stored in FlutterSecureStorage (Android Keystore /
   iOS Keychain). ApiClient auto-refreshes expired access tokens using refresh
   tokens. Sessions persist across app restarts.

10. Are invalid login attempts handled correctly?
    ANSWER: PARTIALLY. The backend returns proper HTTP error codes (400 for bad
    OTP, 401 for invalid tokens), but since OTP verify accepts ANY code, there
    is no real "invalid login" scenario currently. Rate limiting is NOT implemented.

================================================================================
19. Can tournaments be created?
    ANSWER: YES via API (POST /api/tournaments/ — admin only). React admin
    dashboard has a tournament creation page. No tournament creation in Flutter.

20. Can tournaments be edited?
    ANSWER: NO — No API endpoint exists for editing tournaments after creation.

21. Can tournaments be cancelled?
    ANSWER: YES — POST /api/tournaments/{id}/cancel (admin only). Automatically
    refunds all participants' entry fees with REFUND transaction type.

22. Can players join tournaments?
    ANSWER: YES — POST /api/tournaments/{id}/join (authenticated user).
    Flutter tournament detail screen has a Join button.

23. Is the entry fee deducted correctly?
    ANSWER: YES — join_tournament checks wallet balance >= entry_fee, then
    calls WalletService.deduct() with TransactionType.ENTRY_FEE.

24. Is the refund flow implemented?
    ANSWER: YES — On tournament cancellation, WalletService.credit() is called
    for each participant with TransactionType.REFUND. Also works for withdrawal
    rejection.

25. Is winner declaration working?
    ANSWER: PARTIALLY — Match verify endpoint (POST /api/matches/{id}/verify)
    accepts action (approve/reject), winner_id, score, prize_awarded. On approve,
    it credits the winner's wallet and updates user stats. But no dedicated
    "declare winner" flow exists separate from match verification.

26. Is prize distribution working?
    ANSWER: YES — When admin verifies a match with a winner_id and prize_awarded > 0,
    the prize is automatically credited to the winner's wallet via
    WalletService.credit() with TransactionType.PRIZE.

   ANSWER: Twilio (code exists in auth_service.py) but NOT configured.

   TWILIO_PHONE_NUMBER=""

3. If Firebase is used:

   ANSWER: N/A — Firebase is not used for OTP. Firebase is included for
   push notifications (firebase_messaging) only.

4. Is the OTP request reaching the backend?
   ANSWER: YES — POST /api/auth/otp/request works. Backend creates/updates
   the User record and returns success.

5. Is the backend sending the OTP successfully?
   ANSWER: NO — Twilio is not configured, so no SMS is sent. The backend
   returns {"message": "OTP sent successfully"} but nothing is actually sent.

6. Is the SMS provider account configured correctly?
   ANSWER: NO — All Twilio env vars are empty. No SMS provider is configured.

7. Are all required environment variables configured?
   ANSWER: NO — TWILIO_ACCOUNT_SID, TWILIO_AUTH_TOKEN, TWILIO_PHONE_NUMBER
   are all empty. These need real Twilio credentials for SMS delivery.

8. What is the exact console or backend error message?
   ANSWER: No error — the backend silently skips SMS sending when Twilio
   credentials are empty. The OTP is generated but never delivered to the user.
   The frontend shows "Failed to send OTP" because it cannot display the OTP
   to the user — the API response only returns {"message": "OTP sent successfully"},
   not the OTP code itself.

9. Is the emulator configured correctly for OTP testing?
   ANSWER: NO — The emulator needs to reach the backend at 10.0.2.2:8000

   a) A mock OTP that is always "123456" in development mode, OR

   CURRENT BLOCKER: The frontend shows "Failed to send OTP" error.
   This is likely because the backend endpoint DOES work (returns 200),
   but the frontend error handling is catching something else — possibly

FINAL CTO QUESTION
================================================================================
If you had to launch this app to 500 real users tomorrow, what are the TOP FIVE
things that would worry you the most?

1. OTP BYPASS — Anyone can log in as any user with any 6-digit code. This is a
   complete authentication bypass. An attacker could take over any account.

2. NO RATE LIMITING — The auth endpoints, wallet operations, and tournament joins
   have no rate limiting. A simple script could brute-force accounts or drain
   wallets through repeated requests.

3. NO HTTPS — The backend runs on plain HTTP. All JWT tokens, phone numbers, and
   wallet data are transmitted in cleartext. Anyone on the same network can
   intercept everything (MITM attack).

4. WALLET INTEGRITY — No idempotency on wallet transactions. No duplicate
   prevention. Race conditions on concurrent requests could lead to double-
   spending or incorrect balances. The frozen balance model for withdrawals
   is a good start but needs stress testing.

5. ZERO TESTING — No unit tests, no integration tests, no security tests. The
   entire system has only been manually tested by a developer on localhost.
   There is no confidence that edge cases, error handling, or concurrent
   scenarios work correctly.
